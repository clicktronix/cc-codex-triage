# плагин cc-codex-triage

[English](README.md) · [Español](README.es.md) · **Русский**

Постоянные именованные треды Codex CLI для открытого кросс-агентного триажа в Claude Code.

## Что он даёт

- `/ask [--thread <name>] [--oneshot] <вопрос>` — информационные вопросы в постоянном треде (по умолчанию read-only sandbox). «Как тут работает X», «есть ли уже Y». По умолчанию используется общий на репозиторий тред `ask`; передайте `--thread <feature>`, чтобы вопросы по фиче лежали вместе с остальным контекстом Codex по этой фиче.
- `/review [--required --base <ref> --spec <path>] [--lens <name>] [--thread <name>] [--once] [--oneshot] [--cap N] [--model <m>] [--effort <e>] [--background] [--json] [--continue] <текст>` — критика в треде review; **по умолчанию итерирует до APPROVE**. `--required` доступен модели для owning delivery workflow и за один вызов забирает один foreground-раунд. Валидные блокирующие находки возвращаются владельцу для fix/test/commit и нового candidate; опровергнутые или явно отложенные находки повторно ревьюятся на том же immutable candidate, без фиктивного изменения. Первый required-раунд фиксирует base/spec/cap до явного reset треда или перехода в другой тред. Approval создаётся только для явных base/spec и точного неизменившегося clean candidate HEAD/tree/fingerprint. Cap или divergence останавливают flow без approval; background/single-pass/JSON/Judge-mode не удовлетворяют обязательный gate.
- `/plan [--lens <name>] [--thread <name>] [--once] [--oneshot] [--cap N] [--model <m>] [--effort <e>] [--background] <план>` — стресс-тест плана в треде plan; **по умолчанию итерирует до APPROVE**. Линзы: stress-test (по умолчанию), pre-mortem, devils-advocate, alternatives, adr. Линзы плана теперь завершаются машиночитаемым вердиктом (`APPROVE | REQUEST_CHANGES | COMMENT`). `--model`/`--effort` задают модель/уровень reasoning effort, применяются только при первом диспатче или при `--oneshot` (resume сохраняет модель/effort треда стабильными и выдаёт WARN, если передать их снова). `--background` диспатчит в отсоединённом (detached) режиме и возвращает ход, не дожидаясь ответа (подразумевает один проход, без цикла; использует флаг драйвера `--detach` — диспатч выполняется в собственной сессии процессов и переживает зачистку процессов harness'ом — плюс поставляемый watcher `detach-watch.sh`, запускаемый Claude-managed background-задачей: он доставляет ответ или диагностику сбоя уведомлением о завершении).
- `/reply [thread] <директива>` — Claude Code отвечает обратно в активный тред (ответить на вопрос, выполнить запрошенное действие инструментом, оспорить находку).
- `/debate [--rounds N] [--thread <name>] <вопрос>` — структурированное многораундовое разногласие между Claude Code и Codex по какому-то решению, каждый обмен виден пользователю, заканчивается честным синтезом (остаточные разногласия проговариваются, а не замазываются).
- `/autoreview on|off|status` — при взведении, если в ветке уже есть изменения, оно ревьюит их сразу (без ручного `/review`); затем Stop-хук блокирует любой будущий ход, в котором код отличается от последнего состояния, отпущенного гейтом, — пока ревью Codex не достигнет APPROVE, **покрывающего именно это состояние**, либо пока не исчерпан лимит раундов. Единица измерения — **цикл**, а не взведение: отпечаток хеширует *содержимое* рабочего дерева, поэтому исправление переживает собственный коммит и гейт остаётся активным, коммит уже одобренных байтов не стоит ни одного раунда, а один APPROVE отпускает одно состояние, а не всё взведение. Защита от разгона: численно валидируемый лимит раундов на цикл — жёсткий терминатор (битое состояние fail-open), и пополняется он только настоящим релизом. Взведённые гейты **автоматически истекают через 14 дней** — устаревший гейт на давно влитой ветке снимает себя сам, вместо того чтобы сработать заново при повторном использовании имени ветки.
- `/autoplan on|off|status` — то же, что `/autoreview`, но для документов-планов: при взведении, если `docs/plans/**` уже изменён, оно сразу стресс-тестит их; затем блокирует любой будущий ход, в котором документы-планы отличаются от последнего отпущенного состояния, пока тред плана не увидит диспатч в текущем цикле (гейт ловит рост лога, а не идентичность команды). Отпечаток хеширует содержимое, включая untracked-файлы, поэтому план, переписанный после релиза, снова взводит гейт. Та же семантика лимита и автоматического истечения через 14 дней.
- `/thread [--topic <text>] [--oneshot] <name> <сообщение>` — произвольные именованные треды (прямой проброс). `--topic` записывает одну строку о том, что в треде, в момент его создания.
- `/thread-list` — активные треды с раундами, размером лога, последней активностью и **темой**, плюс метка `[busy]`, если по треду идёт диспатч. Печатает `scripts/thread-index.sh` — локальное чтение без вызова Codex, поэтому `codex-second-opinion` может запустить его сам, чтобы переиспользовать подходящий тред вместо создания нового.
- `/thread-new <name> [сообщение]` — принудительный сброс треда (теряет память).
- `/status` — read-only вид на один экран: ветка, рабочее дерево, общий путь state, взведённые гейты и их **состояние цикла**, последний вердикт по каждому треду, состояние required-review гейта (включая живой или протухший
  claim и жёсткую остановку `CAP_REACHED`) и версия Codex CLI.
- `/cleanup [--apply] [--older-than <days>]` — находит устаревшие/pre-0.5 взведённые гейты, осиротевшие логи тредов, устаревшую диагностику last-error, а с `--older-than <days>` — целиком «спящие» треды; по умолчанию dry-run, `--apply` **архивирует** их (никогда не удаляет, обратимо). Предохранители действуют для каждого класса: треды с живой лизой диспатча, свежим согласованным required-review claim или являющиеся целью взведённого гейта никогда не трогаются, а generic-треды `review`/`plan` только перечисляются. Apply закрывается с ошибкой, если gate любого worktree нельзя обнаружить; финальная проверка и перемещения держат mutex диспатча/review и gate-writer.
- `/review-dispute <id> <почему>` / `/review-accept <id> --reason` / `/review-defer <id> --issue` — закрыть зарегистрированную находку ревью по её id (ложноположительная / принятый компромисс / отложена в отслеживаемый issue), чтобы она ушла из списка открытых с аудит-следом, а не была тихо потеряна.
- Skill `codex-triage` документирует маршрутизацию, обрамление Judge-mode, правила анти-капитуляции в дебатах, валидацию входящих находок Codex (проверь перед тем, как применять — не штампуй ради снятия гейта), правило «чинить-окрестность», признак того, что цикл ревью — неподходящий инструмент, и модификатор `--oneshot`.
- `/review` доступен модели, чтобы owning workflow мог самостоятельно довести обязательный review до `APPROVE`. Остальные slash-команды остаются user-only. Skill `codex-second-opinion` по-прежнему делает только один ограниченный диспатч для отдельной развилки и не трогает треды гейтов.

Каждая команда по умолчанию держит постоянный тред Codex; `--oneshot` делает любую из них одноразовой (`codex exec --ephemeral`, состояние не сохраняется). **Одна задача = один тред**: `/review` и `/plan` по умолчанию используют тред, привязанный к ветке (`review-<branch>` / `plan-<branch>`, напр. `review-main` на `main` — без особого случая для main), так что каждая ветка и её соответствующий гейт остаются изолированными; передайте `--thread <topic>`, чтобы разбить дальше, или `--thread review` для общего.

**Одна фича = один тред, поверх команд.** Эти умолчания заданы на *тип команды*, поэтому контекст одной фичи расползается между `ask`, `plan-<branch>` и `debate-<slug>`. Направьте `/ask`, `/plan` и `/debate` в один `--thread <feature>`, а `/review` оставьте на его треде ветки (гейт читает вердикты именно оттуда). Песочница фиксируется при создании сессии Codex — `codex exec resume` принимает `-m` и `--output-schema`, но не `-s`, — поэтому тред фичи выбирает read-only или запись один раз, при первом диспатче. И поскольку каждый resume заново скармливает историю, разросшийся тред стоит разрезать, а не тянуть бесконечно; `/thread-list` показывает раунды и размер. Для калибровки, а не как проверенный порог: продуктовые треды фич доходят до ~130 КБ к девятому раунду, а самый длинный из зафиксированных (13 раундов) так и не сошёлся.

## Чем он отличается от альтернатив

| | Этот плагин | `hamelsmu/claude-review-loop` | `dementev-dev/adversarial-review` |
|---|---|---|---|
| Сессии Codex | **Постоянные через `exec resume`** | Каждый раз новые | Постоянные через `exec resume` |
| Лимит раундов | **`--cap` на цикл команды (по умолчанию 5), отдельный лимит на цикл в гейтах** | 1 | 5 (approve/revise) |
| Назначение | **Итеративный диалог-триаж + опциональный гейт само-проверки** | Многоагентное ревью в один проход | Цикл approve/revise |
| Вывод | Markdown-поток, как есть | Сводный Markdown-файл | JSON + Markdown + литерал VERDICT |

Используйте его, когда разговор будет итеративным. Используйте `claude-review-loop` для одного исчерпывающего ревью. Используйте `adversarial-review`, когда нужен жёсткий гейт pass/fail после ограниченного числа раундов.

## Предварительные требования

- CLI `codex` ≥ 0.137.0 (`npm install -g @openai/codex`) — версия, на которой проверены семантики resume/`--ephemeral`; более старые CLI могут работать, но не тестировались.
- `/review --json` требует `codex` ≥ 0.142 (поддержка `--output-schema`) и `jq`.
- `~/.codex/config.toml` с моделью, на которую у вас есть права. Переопределение на вызов: `CC_CODEX_FLAGS="-m gpt-5.5 -s read-only"`. Ограничение: строка флагов разбивается по пробелам, поэтому значения отдельных флагов не могут содержать пробелы.
- Диспатчи одного треда сериализуются драйвером: второй диспатч при живом первом отклоняется (exit 10, PID-lease + мьютекс захвата) — гонки счётчиков/лога между ними нет. Используйте одну владеющую гейтом сессию Claude Code на worktree и одну задачу на тред. У разных worktree armed-гейты изолированы; сессии, намеренно использующие один тред, по-прежнему разделяют его ledger и review state.

## Где живёт состояние

- `<git-common-dir>/cc-codex-triage/threads/<name>.id` — UUID сессии Codex, общий для всех worktree.
- `<git-common-dir>/cc-codex-triage/threads/<name>.log` — append-only аудит-лог пар prompt/ответ.
- `<name>.candidate`, `<name>.review-state`, `<name>.review-loop`, `<name>.approved` — машинное состояние обязательного review, привязанное к точному кандидату.
- `<absolute-git-dir>/cc-codex-triage/gates/` — armed gates и fingerprint cache текущего worktree; между worktree не разделяются.
- `~/.codex/sessions/rollout-*.jsonl` — собственные rollout-файлы Codex (управляются Codex CLI).

Плагин никогда не удаляет rollout-файлы Codex. `/thread-new` очищает только указатель, счётчики, task metadata и required-review sidecars этого репозитория.

## Примитивы безопасности

- **Никакого тихого нового exec при сбое resume.** Если `codex exec resume` падает, драйвер выходит с кодом 4 и просит вас явно сделать `--new`. Ваша уверенность «Codex это помнит» никогда не ломается молча.
- **Страж мутации версионируемых файлов.** Драйвер снимает снимок `git status --porcelain` до/после каждого диспатча в Codex и предупреждает при расхождении. Поставьте `CC_CODEX_TRIAGE_STRICT=1`, чтобы сделать это фатальным. Запускайте с `CC_CODEX_FLAGS="-s read-only"` для тредов чистого ревью.
- **Никакого `--last`.** Треды привязаны к сохранённому UUID; если он пропал, следующий вызов стартует с нуля, а не с «того, что недавно трогали в `~/.codex/sessions/`».

### Известная избыточная выдача прав: `allowed-tools: Bash`

Каждая команда здесь объявляет голый `allowed-tools: Bash`. Это поле — **предварительная выдача прав, а не ограничение**: на том ходу, где вызвана команда, без запроса разрешения выполнится любая Bash-команда, а не только драйвер плагина. Правильно было бы сузить это до вызова драйвера.

Пока не сужено, и намеренно. Внутри Bash-правил `allowed-tools` документированы подстановки `${CLAUDE_SKILL_DIR}` и `${CLAUDE_PROJECT_DIR}`; `${CLAUDE_PLUGIN_ROOT}` — через который и вызывается всё здесь — среди них нет. Правило, написанное через него, скорее всего останется буквальной строкой, не совпадёт ни с чем и превратит каждый диспатч в запрос разрешения. Менять узкую избыточность прав на сломанный поток — плохая сделка, поэтому это ждёт либо подтверждения, что `${CLAUDE_PLUGIN_ROOT}` там раскрывается, либо переписывания правил через `${CLAUDE_SKILL_DIR}`.

Выданные права действуют только на тот ход, где команда была вызвана, и снимаются на вашем следующем сообщении.

## Обрамление Judge-mode

Когда вы вставляете находки другого агента в `/review`, команда оборачивает prompt как оценку третьей стороны, а не как последовательное опровержение. Эмпирически (arXiv 2509.16533, EMNLP 2025 Findings) это снижает уровень угодливой капитуляции с 23,5–80,3 % в 1,5–2 раза.

## Установка

```
/plugin marketplace add clicktronix/cc-codex-triage
/plugin install cc-codex-triage@cc-codex-triage
```

(Суффикс `@cc-codex-triage` — это имя marketplace: `plugin@marketplace`.)

Команды плагина **пространственно именованы** (namespaced) под плагином. Вызывайте их как
`/cc-codex-triage:review`, `/cc-codex-triage:ask` и т. д. Короткая форма `/<name>`
тоже работает для имён, не сталкивающихся со встроенными, — но `/review` и
`/plan` заняты собственными командами Claude Code, поэтому для этих двух используйте форму с namespace.

## Что сознательно не входит

**Этап груминга / предварительного планирования** — когда два харнеса собирают
контекст и обсуждают задачу *до* того, как пользователя ведут по опроснику
требований — рассмотрен и намеренно оставлен снаружи. Все нужные детали здесь
уже есть (`/ask` на треде фичи, `/debate`, `/plan`), но сам этап живёт выше
этого плагина — в том, что ведёт задачу: он должен владеть опросником и решать,
что ещё стоит спрашивать. Строить его здесь значило бы, что плагин лезет в
процесс, в котором он лишь участник.

## Область: однонаправленно (Claude Code → Codex CLI)

Это плагин **Claude Code**. Его slash-команды вызывают CLI `codex`
через встроенный драйвер. Он намеренно не упакован как плагин Codex
(`.codex-plugin/`) — Codex'у нечего запускать; Codex здесь вызываемый, а не
хост. Если вы хотите, чтобы Codex *хостил* skills — это другой артефакт.
